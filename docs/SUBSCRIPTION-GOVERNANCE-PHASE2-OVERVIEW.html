01

왜 이 프로젝트인가

SaaS 도입이 계열사별로 자유롭게 이뤄지면서 비용은 계속 늘고 있는데, 그 전체를 한눈에 보는 사람은 없었다. 경영진은 이 상황을 더 이상 두고 볼 수 없다는 입장이고, 그 컨트롤타워 역할을 자산관리파트가 맡기로 했다.

기존 통합 관제 체계

문제의 본질은 두 가지가 겹쳐 있다. 첫째, 계열사마다 도메인과 운영 방식이 달라 표준 프로세스를 강제하기 어렵다. 둘째, 구독형 SaaS는 등록 이후 방치되기 쉬운 구조라 — 담당자가 바뀌거나 실사용이 끊겨도 결제는 계속된다. 이 두 가지를 동시에 풀지 못하면 "관리하고 있다"는 착시만 남는다.

02

세 관점의 요구를 동시에 만족시켜야 한다

이 기획은 어느 한쪽만 만족시키면 실패한다. 운영자·사용자·임원, 세 관점의 요구가 서로 다른 방향을 향할 수 있어서 설계 단계부터 함께 고려했다.

👤 운영자 (자산관리파트)

혼자서 17개 이상 계열사를 관리해야 한다.

  • 반복 작업 최소화(대사·환율 자동 계산)
  • 이상 징후를 스스로 찾기보다 시스템이 먼저 알려주길 원함
  • 계열사 간 표기 차이로 인한 집계 오류 부담

🏢 사용자 (계열사 담당자)

각자의 법인 데이터만 보고, 등록·갱신을 직접 처리한다.

  • 본인 법인 범위를 벗어난 데이터는 볼 필요도 권한도 없어야 함
  • 등록 절차가 복잡하면 방치로 이어짐
  • 메일 폭탄이 아니라 필요할 때 화면에서 확인하고 싶어함

💼 임원 · 경영진

비용 증가를 통제하고 싶고, 컨트롤타워가 이 파트이길 기대한다.

  • 전사 지출 추세를 화면 몇 개로 파악하고 싶음
  • 중복·낭비 지출을 구조적으로 찾아내길 원함
  • 세부 구현보다 "결론"과 "절감 여지"에 관심
설계 원칙 — 임원용 화면은 요약과 결론 위주(거버넌스 스코어카드, 벤더 통합 뷰, 월간 리포트), 운영자용 화면은 자동 판정과 대사 중심(이상치·중복탐지·카드명세 대사), 사용자용 화면은 권한 스코프가 걸린 최소 입력 폼으로 나눠 설계했다.
03

전체 아키텍처 개요

클라우드 DB 비용과 관리자 1인 체계라는 현실적 제약 위에서 만들어진 구조다. "이상적인" 인프라가 아니라 "지금 감당 가능한" 인프라를 택했다.

flowchart LR
    subgraph MAC["맥 1대 — 중앙 DB"]
        PG[("Postgres\n(Self-hosted Supabase)")]
        TF["Tailscale Funnel\n(HTTPS 노출)"]
        PG --- TF
    end
    APP["SW-PORTAL\n(Next.js · Vercel)"]
    NOTION[("Notion\n5분 주기 단방향 백업")]
    USERS["계열사 담당자\n(17개+)"]
    EXEC["임원 · 대표"]

    TF <--> APP
    PG -. 백업 전용, 앱은 직접 안 씀 .-> NOTION
    USERS --> APP
    EXEC --> APP
앱은 항상 Postgres를 1차 소스로 읽고 쓴다. Notion은 장애 대비 백업일 뿐 실시간 데이터 소스가 아니다 — 과거 "Notion 조회 지연 + 캐시 비용" 문제를 겪은 뒤 내린 결정이다.

이 구조를 유지하기 위해 두 가지 대안을 검토했지만 모두 최종 채택하지 않았다 — 자세한 사유는 07. 제외한 것과 이유에 정리했다.

04

1차 개발 — 이미 구축된 기반 완료

구독형 SaaS 관리의 기본 뼈대다. 이상치를 잡아내고, 환율을 결제 시점 기준으로 정확히 계산하고, 카드명세와 대사하고, 임원이 한눈에 볼 수 있는 거버넌스 화면까지 — 이 위에 2차 개발이 얹힌다.

05

2차 개발 로드맵 (G1~G13)

1차가 "기반"이라면 2차는 "빈틈 메우기"다 — 계정이 방치돼도 모르는 문제, 중복 지출이 표기 차이로 숨는 문제, 해지 결정이 유실되는 문제 등, 운영하면서 드러난 실제 구멍들이다. 구현 순서와 각 항목의 코드 수준 설계는 SUBSCRIPTION-GOVERNANCE-PHASE2.md에 있고, 여기서는 전체 그림과 왜 이 순서인지만 다룬다.

06

SaaS 벤더 API 연동 전략

"종량제 라이선스는 GPT처럼 API로 데이터를 가져오자"는 방향에서 출발했다. 그런데 실제 SW 현황을 보면 이 요청은 사실 성격이 다른 두 가지가 섞여 있었다 — 나눠서 봐야 헛수고를 피할 수 있다.

① 종량제 비용 추적형

실사용량만큼 청구되는 서비스

OpenAI · Anthropic · AWS/Azure/GCP

  • 목적: 실제 청구액을 예산 상한과 실시간 비교
  • API 연동의 실익이 가장 큰 그룹
  • 1단계 파일럿 대상
② 좌석 사용률 대사형

좌석 단위로 정액 결제되는 서비스

Microsoft 365 · Slack · Zoom · Adobe

  • 목적: 산 좌석 수 vs 실제 로그인한 사용자 수 비교
  • 청구액은 API로 가져올 실익이 적음(이미 계약서에 고정)
  • 미사용 좌석 탐지에 집중 — 재확인 캠페인(G6)의 자동화 버전
카테고리벤더확보 가능 데이터연동 가능성
AIOpenAI (ChatGPT Enterprise/Team)사용량, 청구 내역, 멤버 목록파일럿 1순위
AIAnthropic (Claude Enterprise)사용량·비용, 멤버 목록파일럿 1순위
AIGitHub Copilot좌석 수, 활성 사용자가능
개발GitHub (Org/Enterprise)좌석 수, 청구액가능
개발AWS / Azure / GCP실제 클라우드 비용가능(우선순위 낮음)
디자인Adobe Creative Cloud라이선스 배정 현황부분 가능
문서작성Microsoft 365라이선스, 활성 사용자 리포트전역관리자 협조 필요
문서작성Google Workspace라이선스, 활성 사용자보류 — GWS 미도입

진행 순서는 OpenAI·Anthropic(1단계) → GitHub(2단계) → Microsoft 365(3단계) 이고, Google Workspace는 회사가 도입하기 전까지는 대상이 아니다. 각 단계마다 필요한 것은 개발보다 협조다 — 벤더 API는 대부분 조직 관리자 권한이 있어야 키를 발급받을 수 있고, Enterprise 등급 이상에서만 제공되는 경우가 많아 벤더 영업 담당자 확인이 선행돼야 한다.

07

검토했지만 채택하지 않은 것 — 의사결정 로그

"왜 이렇게 안 했지?"라는 질문이 나중에 다시 나올 때, 재검토 없이 바로 참고할 수 있도록 기록해둔다.

검토 항목검토 배경결론사유
자체 OAuth 2.0 SSO 구축 향후 GWS(Google Workspace) 도입 가능성을 대비한 사전 검토 범위 제외 도입 시점이 불확실한 상태에서 자체 인가서버까지 만드는 건 유지부담 대비 실익이 낮음. 대신 "Google로 로그인"(G10)만 기존 ID/PW와 병행 추가 — GWS가 나중에 도입돼도 코드 변경 없이 그대로 동작
Windows 콜드스페어 물리 서버 맥 1대 운영 체계의 가용성 리스크 검토, 별도 PC 추가 논의 구축 후 철회 실제로 인프라(문서·백업 스크립트)까지 구축했으나, 최종적으로 "맥 하나로 통일"하는 쪽으로 결정 변경 — git revert로 깔끔히 되돌림. 가용성 문제 자체는 여전히 유효하나 별도 논의로 이관
자동 메일 알림 (F5 원안) 원 기획서상 갱신임박·예산초과를 이메일로 발송하는 요구 화면 표시로 대체 과거 평가 메일 중복발송 사고 이력이 있고, 원인이 됐던 발송용 크론도 이미 제거된 상태 — 같은 실패 패턴을 다시 들이는 대신 "화면에서 확인"으로 설계 변경
08

운영 원칙

기능이 늘어나도 지켜야 하는 최소한의 가드레일. 새로 합류하는 개발자도 이 원칙만은 예외 없이 따라야 한다.

발송은 화면까지만

메일·알림 자동 발송 기능은 만들지 않는다. 발송 관련 결정은 반드시 별도 승인을 받는다.

실패는 실패로 보인다

데이터 쓰기 실패를 성공으로 착각한 응답을 절대 보내지 않는다 — 과거 실제 사고 이력이 있다.

키는 코드에 남기지 않는다

외부 벤더 API 키·토큰은 환경변수로만 관리한다. 로그인 정보보다 유출 피해가 크다.

추가는 항상 additive

기존 화면·데이터를 뜯어고쳐야 하면 반드시 먼저 확인받는다.

배포는 승인 후에만

커밋·푸시·머지·프로덕션 반영은 명시적 승인 없이 진행하지 않는다.

기능 = 커밋 단위

여러 기능을 한 커밋에 섞지 않는다. 완료 후에는 무엇을 바꿨는지 요약 보고한다.
