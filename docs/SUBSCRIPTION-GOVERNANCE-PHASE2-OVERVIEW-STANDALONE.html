01

왜 이 프로젝트인가

SaaS 도입이 계열사별로 자유롭게 이뤄지면서 비용은 계속 늘고 있는데, 그 전체를 한눈에 보는 사람은 없었다. 경영진은 이 상황을 더 이상 두고 볼 수 없다는 입장이고, 그 컨트롤타워 역할을 자산관리파트가 맡기로 했다.

기존 통합 관제 체계

문제의 본질은 두 가지가 겹쳐 있다. 첫째, 계열사마다 도메인과 운영 방식이 달라 표준 프로세스를 강제하기 어렵다. 둘째, 구독형 SaaS는 등록 이후 방치되기 쉬운 구조라 — 담당자가 바뀌거나 실사용이 끊겨도 결제는 계속된다. 이 두 가지를 동시에 풀지 못하면 "관리하고 있다"는 착시만 남는다.

02

세 관점의 요구를 동시에 만족시켜야 한다

이 기획은 어느 한쪽만 만족시키면 실패한다. 운영자·사용자·임원, 세 관점의 요구가 서로 다른 방향을 향할 수 있어서 설계 단계부터 함께 고려했다. 세 관점 모두 결국 같은 앱(Assetify Desktop) 화면을 역할(super/admin/company/general)에 따라 다르게 쓰게 된다.

운영자 — 자산관리파트

혼자서 17개 이상 계열사를 관리해야 한다.

  • 반복 작업 최소화(대사·환율 자동 계산)
  • 이상 징후를 스스로 찾기보다 시스템이 먼저 알려주길 원함
  • 계열사 간 표기 차이로 인한 집계 오류 부담

사용자 — 계열사 담당자

같은 앱을 company 스코프 계정으로 설치해 자기 법인 데이터만 등록·갱신한다.

  • 본인 법인 범위를 벗어난 데이터는 볼 필요도 권한도 없어야 함
  • 등록 절차가 복잡하면 방치로 이어짐
  • 메일 폭탄이 아니라 필요할 때 화면에서 확인하고 싶어함

임원 · 경영진

비용 증가를 통제하고 싶고, 컨트롤타워가 이 파트이길 기대한다.

  • 전사 지출 추세를 화면 몇 개로 파악하고 싶음
  • 중복·낭비 지출을 구조적으로 찾아내길 원함
  • 세부 구현보다 "결론"과 "절감 여지"에 관심
설계 원칙 — 임원용 화면은 요약과 결론 위주(거버넌스 스코어카드, 벤더 통합 뷰, 월간 리포트), 운영자용 화면은 자동 판정과 대사 중심(이상치·중복탐지·카드명세 대사), 사용자용 화면은 권한 스코프가 걸린 최소 입력 폼으로 나눠 설계한다.

"관리자 PC"는 실제로는 여러 대다(super/admin 및 각 계열사 company 계정 담당자) — 각자 독립된 Electron 프로세스로 같은 맥 서버에 동시에 접속한다. SW-PORTAL 웹은 없어지지 않는다 — 문의 접수·자산 실사·수요조사처럼 사내 누구나 접근해야 하는 공개 신청 폼은 계속 웹으로 남고, 그 데이터가 같은 Postgres에 쌓이면 Assetify Desktop이 조회·처리한다.

클라이언트 안에서: 왜 로컬 SQLite가 있고, 왜 매번 비우는가

electron-updater를 쓰지 않는다 — 서명(코드사이닝) 없이 내부 배포하기 때문에 macOS의 자동 설치 검증을 애초에 통과할 수 없어, 아예 자체 KV 매니페스트 + Vercel Blob 비공개 저장소 조합으로 대체했다. Windows만 자동 설치가 가능하고, macOS는 DMG를 열어주는 데까지가 앱의 역할이다.

04

지금 상태 — 무엇이 어디에 있나

이전 버전 문서는 F1~F7과 거버넌스 스코어카드·벤더 통합 뷰를 "완료"로 표시했다. 정정한다 — 완료된 곳은 SW-PORTAL 웹의 관리자 화면(sw-portal-next)이고, 실제 배포 대상인 Assetify Desktop에는 아직 이식되지 않았다.

기능SW-PORTAL 웹(sw-portal-next)Assetify Desktop
SW 기본 CRUD(등록·수정·삭제·엑셀 업로드)있음이식됨
구독 현황 리포트(부서별 집계)있음구버전만 이식됨 — 이상치·환율이력화 이전 로직
F1 이상치 경고 / F3 환율 이력화(결제일 기준)있음없음
F4 카드명세 업로드·대사있음없음
F5 알림(갱신임박·예산초과, 화면표시)있음없음
거버넌스 스코어카드 / 계열사 그룹핑있음없음
벤더 통합 협상 뷰있음없음
설치 SW 화이트/블랙리스트 감사—있음(별개 기능, sw-audit.ts)
결론 — G1~G13을 시작하기 전에, F1~F7·거버넌스 스코어카드·벤더 통합 뷰를 Assetify Desktop으로 옮기는 작업이 먼저 필요하다. 아래 로드맵의 G0이 그 작업이다.

다행인 점 — 이식은 재설계가 아니다

Assetify Desktop의 src/main/api/router.ts는 Next.js의 NextRequest/NextResponse와 호환되는 얇은 shim을 이미 갖추고 있다. 그래서 app/api/report/route.ts 같은 웹 라우트 파일을 src/main/api/routes/에 거의 그대로 복사하고, src/main/api/registry.ts에 경로 한 줄만 등록하면 대부분 동작한다. 화면(컴포넌트)도 fetch("/api/...") 호출부만 window.electronAPI.apiCall(...)로 바꾸면 나머지 UI 코드는 그대로 옮겨진다. 즉 설계는 이미 끝나 있고, 남은 건 기계적인 포팅이다.

05

개발 진행 방식

이 문서가 하는 일과 하지 않는 일을 먼저 구분한다 — "왜 필요한지, 무엇을 만들지, 어떤 순서로 할지, 전체 구조가 어떻게 생겼는지"까지가 이 문서의 몫이다. "정확히 어떤 파일의 어느 부분을 어떻게 고치는지"는 여기 없다 — 그건 각 티켓에 착수하는 시점에 별도 MD로 새로 쓴다.

왜 사전에 전부 문서화하지 않는가 — 코드를 실제로 열어보기 전에 세부까지 미리 써두면, 그 전제가 틀렸을 때 통째로 버려야 한다. 방금 이 문서에서 그 일이 실제로 일어났다 — "웹 포털"이라는 전제 하나가 틀려서 아키텍처와 로드맵 전체를 다시 썼다. 코드베이스를 실제로 연 직후에 쓴 지침이, 코드를 안 보고 미리 쓴 지침보다 항상 정확하다.

티켓 착수 절차

1. 티켓 선택

우선순위표와 의존성 다이어그램(06장)에서 선행 티켓부터 고른다 — G0이 항상 먼저다.

2. 코드 확인

core/*, src/main/api/routes/*, src/renderer/src/components/*를 실제로 열어 이 문서의 설계 설명이 지금도 맞는지 확인한다. 틀렸으면 코드를 짜기 전에 이 문서부터 고친다.

3. 티켓 MD 작성

docs/tickets/<티켓ID>-<한줄요약>.md로 배경·설계·수용기준·Claude Code 프롬프트를 새로 쓴다. 코드를 방금 본 뒤라 사전 작성보다 정확하다.

4. 구현 · 검증

그 문서로 구현 → npm run typecheck → 앱을 직접 실행해 화면으로 확인한다.

5. 버전 · 커밋

CLAUDE.md 버전 규칙대로 patch/minor를 올린다. 수정 하나마다 — 여러 개를 모아 한 번에 올리지 않는다.

6. 보고 · 다음 티켓

무엇을 바꿨는지 한 문단으로 보고하고 다음 티켓으로 이동한다.

이 문서가 계속 담당하는 것

바뀔 일이 적은 것들 — 배경/취지(01), 세 관점의 요구(02), 전체 아키텍처(03), 우선순위와 그 이유(06), 벤더 API 전략(07), 제외 결정 로그(08), 운영 원칙(09). 티켓별 MD가 매번 새로 쓰이고 버려져도 이 문서는 그 기준점으로 남는다 — 티켓 MD를 쓸 때 이 문서와 어긋나는 걸 발견하면, 코드가 아니라 이 문서를 먼저 의심하고 고친다.

06

로드맵 (G0~G13)

G0(이식)이 새로 추가된 선행 단계다. G1~G13의 배경·취지는 이전 버전과 동일하되, 실행 위치만 app/api/*/route.ts + components/admin/*.tsx(웹)에서 src/main/api/routes/*.ts + src/renderer/src/components/*.tsx(데스크탑)로 바뀐다. 티켓별 세부 지침은 지금 쓰지 않는다 — 05장대로 착수 시점에 새로 쓴다.

순서티켓상태왜 필요한가

07

SaaS 벤더 API 연동 전략

"종량제 라이선스는 GPT처럼 API로 데이터를 가져오자"는 방향에서 출발했다. 그런데 실제 SW 현황을 보면 이 요청은 사실 성격이 다른 두 가지가 섞여 있었다 — 나눠서 봐야 헛수고를 피할 수 있다.

① 종량제 비용 추적형

실사용량만큼 청구되는 서비스

OpenAI · Anthropic · AWS/Azure/GCP

  • 목적: 실제 청구액을 예산 상한과 실시간 비교
  • API 연동의 실익이 가장 큰 그룹
  • 1단계 파일럿 대상
② 좌석 사용률 대사형

좌석 단위로 정액 결제되는 서비스

Microsoft 365 · Slack · Zoom · Adobe

  • 목적: 산 좌석 수 vs 실제 로그인한 사용자 수 비교
  • 청구액은 API로 가져올 실익이 적음(이미 계약서에 고정)
  • 미사용 좌석 탐지에 집중 — 재확인 캠페인(G6)의 자동화 버전
카테고리벤더확보 가능 데이터연동 가능성

진행 순서는 OpenAI·Anthropic(1단계) → GitHub(2단계) → Microsoft 365(3단계) 이고, Google Workspace는 회사가 도입하기 전까지는 대상이 아니다. Assetify Desktop은 요청마다 뜨고 사라지는 서버리스 함수가 아니라 계속 켜져 있는 하나의 프로세스라서, 벤더 API 폴링 주기를 잡기가 오히려 웹 서버리스 환경보다 단순하다 — 이미 같은 방식(20초 폴링, live-sync.ts)으로 자체 데이터도 동기화하고 있다.

08

검토했지만 채택하지 않은 것 — 의사결정 로그

"왜 이렇게 안 했지?"라는 질문이 나중에 다시 나올 때, 재검토 없이 바로 참고할 수 있도록 기록해둔다. 배포 대상이 웹에서 데스크탑으로 바뀌어도 아래 결정은 그대로 유효하다.

검토 항목검토 배경결론사유
자체 OAuth 2.0 SSO 구축 향후 GWS(Google Workspace) 도입 가능성을 대비한 사전 검토 범위 제외 도입 시점이 불확실한 상태에서 자체 인가서버까지 만드는 건 유지부담 대비 실익이 낮음. 대신 "Google로 로그인"(G10)만 기존 ID/PW와 병행 추가 — GWS가 나중에 도입돼도 코드 변경 없이 그대로 동작
Windows 콜드스페어 물리 서버 맥 1대 운영 체계의 가용성 리스크 검토, 별도 PC 추가 논의 구축 후 철회 실제로 인프라(문서·백업 스크립트)까지 구축했으나, 최종적으로 "맥 하나로 통일"하는 쪽으로 결정 변경 — git revert로 깔끔히 되돌림. 가용성 문제 자체는 여전히 유효하나 별도 논의로 이관
자동 메일 알림 (F5 원안) 원 기획서상 갱신임박·예산초과를 이메일로 발송하는 요구 화면 표시로 대체 과거 평가 메일 중복발송 사고 이력이 있고, 원인이 됐던 발송용 크론도 이미 제거된 상태 — 같은 실패 패턴을 다시 들이는 대신 "화면에서 확인"으로 설계 변경
electron-updater(Squirrel) 자동 업데이트 Electron 표준 업데이트 방식 검토 채택 안 함 내부 배포라 코드 서명을 하지 않는데, macOS의 Squirrel.Mac은 서명 검증을 통과해야 자동 설치가 동작한다 — 서명 없이는 어차피 못 쓴다. 대신 KV 매니페스트 + Vercel Blob 비공개 저장소로 자체 구현(이미 assetify-for-desktop에 존재)
09

운영 원칙

기능이 늘어나도 지켜야 하는 최소한의 가드레일. assetify-for-desktop의 CLAUDE.md에 이미 있는 작업 규칙과 충돌하지 않도록 맞췄다.

발송은 화면까지만

메일·알림 자동 발송 기능은 만들지 않는다. 발송 관련 결정은 반드시 별도 승인을 받는다.

실패는 실패로 보인다

데이터 쓰기 실패를 성공으로 착각한 응답을 절대 보내지 않는다 — 과거 실제 사고 이력이 있다.

키는 코드에 남기지 않는다

외부 벤더 API 키·토큰은 환경변수로만 관리한다. 로그인 정보보다 유출 피해가 크다.

추가는 항상 additive

기존 화면·데이터를 뜯어고쳐야 하면 반드시 먼저 확인받는다.

이식은 포팅, 재설계 아님

G0은 웹 admin의 로직을 그대로 옮기는 작업이다. 옮기면서 "더 낫게" 고치려 하지 않는다(별도 티켓으로 분리).

버전 규칙을 따른다

수정 하나마다 patch/minor를 올린다(CLAUDE.md 버전 규칙). 버전을 안 올리고 재빌드하면 이전 배포 파일을 덮어쓴다.
